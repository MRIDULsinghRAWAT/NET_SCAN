\begin{abstract}
When we run network security scans today, we usually get long text reports that list separate vulnerabilities. This makes it hard to see the bigger picture of how an entire network might be at risk. To solve this, we built NET\_SCAN, a real-time tool that goes beyond basic port scanning. NET\_SCAN automatically draws graphs of possible attack paths, showing how a hacker could link different vulnerabilities together. It uses Cyber Kill Chain modeling and MITRE ATT\&CK mapping to do this. We programmed it to find these paths using BFS (to find the shortest path) and Dijkstra's algorithm (to find the deadliest path). It also calculates a Network Exposure Score (NES) to tell us exactly how risky the network is. We tested NET\_SCAN on eight different networks. These included a campus Wi-Fi, VirtualBox setups, public internet hosts, a local SMB host, and a public DNS server like 8.8.8.8. Our tests showed that the tool successfully sorts nodes into Entry, Pivot, and Target roles. It pulls CVE data directly from the NVD, maps MITRE techniques, and scores the network from 0 (clean) to 100 (critical) all in real time.
\end{abstract}

\section{Introduction}
% ============================================================
As computer networks grow larger and more connected, securing them gets a lot harder. Tools we use every day, like Nmap and Nessus, are great at finding flaws in single machines. However, they don't do a great job showing how an attacker could string those flaws together \cite{nmap_ref, nessus_ref}. Just finding a single weak machine isn't enough anymore. We need to be able to see the exact paths an attacker might take to move deeper into the network, which is known as lateral movement.

Figuring out these attack paths by hand is incredibly time-consuming and usually requires an expert red team. To fix this problem, we created \textbf{NET\_SCAN}. This is an automated tool that simulates and maps attacks. It takes basic port scan data, looks up vulnerabilities using the National Vulnerability Database (NVD) \cite{nvd_ref}, and uses our custom algorithms to draw potential kill chains on an interactive graph. By turning plain text data into a visual graph, it becomes much easier to see the blast radius of an attack and figure out which systems to patch first, using our Network Exposure Score (NES).

The main things we achieved in this work are:
\begin{itemize}
    \item We built a fully automated pipeline that connects TCP port scanning, CVE lookups, and kill-chain mapping into one browser interface.
    \item We wrote a critical path engine that runs both BFS and Dijkstra algorithms to find and rank lateral movement paths based on risk.
    \item We developed a way to automatically guess pivot paths by mapping MITRE ATT\&CK techniques to the discovered services.
    \item We created the Network Exposure Score (NES), a math-based formula that scores network risk from 0 to 100.
    \item We proved the tool works by testing it on \textbf{eight} different networks, including local test setups and live internet hosts like a public DNS resolver.
    \item We added a ``What-If'' feature that lets you simulate fixing a vulnerability to instantly see how much it would improve your NES score.
\end{itemize}

\section{Related Work}
% ============================================================
A lot of research has already been done on creating attack graphs \cite{ammann2002}. For example, BloodHound \cite{bloodhound} totally changed how we secure Active Directory (AD) by using graphs to find hidden paths attackers use to gain higher privileges. The limitation with BloodHound is that it mostly focuses just on AD environments.

With NET\_SCAN, we wanted to bring that same visual approach to regular TCP/IP networks. Instead of just giving a static report, NET\_SCAN calculates how strong the network is right now and streams the visual graph live to the browser. What really makes NET\_SCAN different is its Critical Paths engine. We decided to run both BFS and Dijkstra's algorithm at the same time. This lets us see both the shortest path an attacker could take and the most dangerous one, all at once.

\section{System Architecture}
% ============================================================
We split the tool into two main parts: a Python backend that handles the heavy lifting like scanning and intelligence gathering, and a frontend built with React and HTML5 Canvas to draw the graphs.

\subsection{Heuristic Kill Chain Classification}
When NET\_SCAN finds an open service, it automatically tries to figure out what role it plays in an attack. We break them down into three categories:
\begin{itemize}
    \item \textbf{Entry Nodes:} Things like web servers (ports 80, 443) or FTP that are exposed to the outside and give an attacker their first foothold.
    \item \textbf{Pivot Nodes:} Services like SSH or RDP that an attacker could use to hop into deeper, more restricted parts of the network.
    \item \textbf{Target Nodes:} The final goal of the attack, like a DNS server or a Domain Controller holding sensitive data.
\end{itemize}

\subsection{Automated Lateral Movement Modeling}
NET\_SCAN guesses how these nodes connect (like going from $Entry \rightarrow Pivot \rightarrow Target$) by looking at MITRE techniques. For example, it checks for techniques like Exfiltration Over Alt Protocol (T1048) or Exploiting Remote Services (T1210). To decide if a path is actually usable by a hacker, it checks the live CVE data it pulls from the NVD.

\subsection{Critical Paths Engine}
Our Critical Paths Engine is unique because it runs two graph algorithms at the same time:
\begin{itemize}
    \item \textbf{BFS (Shortest Path):} This finds the quickest way to a target node, counting the fewest number of jumps.
    \item \textbf{Dijkstra (Deadliest Path):} This looks at the CVSS severity scores of the vulnerabilities. It finds the path that has the most critical flaws, which we label as \textsc{deadliest} in the app.
\end{itemize}
Every path gets a hop count and a Risk score so you know exactly which paths are the most dangerous.

\subsection{Network Exposure Score (NES)}
To give the network a simple grade, we created the NES. It combines the CVSS 3.1 scores of the vulnerabilities with the number of possible attack paths.
Here is the math behind the NES ($S_{exp}$):
\begin{equation}
S_{exp} = \sum_{i=1}^{N} (w_{cve}^{(i)} \times D_{node}^{(i)}) \times \alpha^{P}
\end{equation}
In this formula, $w_{cve}^{(i)}$ is how severe the vulnerability is, $D$ is the depth, $P$ is the number of lateral paths, and $\alpha$ is a multiplier for the blast radius. We scale the final result from 0 to 100 and group it into four tiers: Low (0--30), Medium (31--59), High (60--80), and Critical (81+).

\subsection{What-If Mitigation Engine}
We built a ``What-If'' feature so you can play around with the graph. You can click on a vulnerable service and simulate taking it offline. When you do this, NET\_SCAN recalculates the NES and the attack chains instantly. This lets you see exactly how much safer your network would be if you patched a specific bug. We tested this heavily on Networks C and F and found it perfectly tracked how much the risk dropped when we disabled certain ports.

\begin{itemize}

    \item \textbf{Network B (VirtualBox FTP Host):} Target IP \texttt{10.9.7.187} --- A local virtual machine running an old, vulnerable FTP server.
    \item \textbf{Network C (VirtualBox Multi-Service):} Target IP \texttt{192.168.56.1} --- Our VirtualBox host gateway running several services at once.
    \item \textbf{Network D (Mobile Hotspot Bridge):} Target IP \texttt{192.168.137.1} --- A Windows mobile hotspot network.
    \item \textbf{Network E (Public Internet Host 1):} Target IP \texttt{208.67.222.222} --- OpenDNS's public server. We found five open ports, resulting in a Critical NES of 85.
    \item \textbf{Network F (Public Internet Host 2):} Target IP \texttt{185.222.222.222} --- This was the most complex network we scanned, hitting our max NES of 100.
    \item \textbf{Network G (Local SMB Host):} Target IP \texttt{172.20.10.3} --- Our own Wi-Fi adapter running Windows file sharing. It scored a Medium NES of 50.
    \item \textbf{Network H (Google Public DNS):} Target IP \texttt{8.8.8.8} --- Google's famous DNS server. We scanned it to see how our tool handles a highly secure public server. It scored a High NES of 60.
\end{itemize}

\subsection{Scan Configuration}
We ran all these tests directly from our NET\_SCAN web dashboard using these settings:
\begin{itemize}
    \item \textbf{Port Range:} 1--1024 (the standard well-known ports).
    \item \textbf{Timeout:} 120--145ms per port.
    \item \textbf{Threads:} 1 (we scanned one by one so we could reproduce the results perfectly).
    \item \textbf{CVE Lookups:} Live queries to the NVD API v2.0.
    \item \textbf{Path Finding:} BFS and Dijkstra algorithms running immediately after the scan.
\end{itemize}

\noindent\textit{Ethical Note:} When scanning public IPs (Networks E, F, and H), we only sent harmless TCP SYN packets to ports 1--1024. We didn't try to actually exploit anything or send malicious payloads.

\subsection{Critical Paths Engine: BFS vs. Dijkstra Validation}
A key novel contribution validated across Networks E, F, and H is the dual-algorithm Critical Paths Engine. Network H provides a particularly instructive case: the topology produces only \textsc{Shortest} paths (no BFS/Dijkstra divergence), indicating that direct 1-hop connections to the DNS target dominate both shortest-hop and highest-risk traversal. By contrast, Networks E and F demonstrated significant BFS/Dijkstra divergence, where 2-hop Dijkstra paths through SSH pivot nodes scored Risk $\approx 19.3$--19.7, far exceeding the 1-hop BFS Risk of 8.7--8.9. This divergence validates that hop-count alone is an insufficient proxy for attack risk---a distinction invisible to conventional traceroute-based tools but captured natively by NET\_SCAN.

\subsection{What-If Mitigation Engine Validation}
The What-If Analysis Engine was validated across Networks C, F, and implicitly G. For Network F, removing Port 53 (DNS) eliminated 4 lateral paths ($-$5 pts NES, 5 remaining paths); removing Port 80 (nginx) eliminated 3 further paths ($-$5 pts). For Network C, decommissioning SMB (Port 445) or NetBIOS (Port 139) each reduced NES by 20 points, and removing RPC (Port 135) reduced it by a further 10 points. These results confirm that the What-If engine delivers precise, node-level remediation prioritization that aligns with the NES formula's lateral compounding logic.

\section{Discussion}
% ============================================================
Building NET\_SCAN proved that combining real-time kill-chain mapping with basic discovery scans solves a huge problem in network security. Our tests across the eight environments highlighted a few major takeaways:

\begin{enumerate}
    \item \textbf{No False Positives:} Networks A and D proved that our tool doesn't cry wolf. If there are no exposed services, it gives a clean score of zero.
    \item \textbf{Working CVE Lookups:} The tool successfully pulled data from the NVD for both our local test machines and the live internet hosts.
    \item \textbf{Path Count Matters Most:} Networks C and G had a NES of 50, but Network H scored a 60. Even though they had similar vulnerabilities, Network H scored higher simply because it had 2 lateral paths compared to zero. This proves that having a path is riskier than just having a bug.
    \item \textbf{BFS vs. Dijkstra Works:} On simpler networks like Network H, both algorithms found the same paths. But on complex ones like E and F, Dijkstra found deadlier, multi-hop paths that BFS missed. This proved why running both at the same time is necessary.
    \item \textbf{MITRE Context:} Mapping to MITRE techniques gave us a much better idea of what an attacker might actually do, even on less critical networks.
    \item \textbf{Internet-Ready:} Testing against real servers like 8.8.8.8 proved that NET\_SCAN doesn't just work in a lab; it works on the real internet.
    \item \textbf{What-If is Actionable:} On Network F, the What-If tool showed exactly how many points the NES would drop if we closed a specific port. You just can't get that kind of clear priority list from a standard CVE report.
\end{enumerate}

\textbf{Limitations.} Right now, NET\_SCAN maps paths between services on a single IP address. We did this on purpose to keep it fast, but eventually, we want it to map paths across entire subnets involving multiple machines. Also, our NVD lookups sometimes brought back really old CVEs (from 1999) because the services matched old fingerprints. The system can easily find modern CVEs too, as long as the banner grabber identifies the modern version properly.

A traditional scanner would look at Networks G and H and say they are equally risky because they both have 6 CVEs. NET\_SCAN knows better. It scores them 50 and 60, respectively, because it can see the lateral paths.

In the future, we plan to add machine learning to predict attack paths, add support for IPv6, and connect NET\_SCAN directly to tools like SIEM or SOAR to automate the fixes.

\section{Proposed Remediation Framework}
% ============================================================
NET\_SCAN is great at finding vulnerable paths and calculating the NES, but what do you do once you find them? How do you actually fix it? To answer this, we came up with a clear step-by-step framework using \textbf{Wireshark} \cite{wireshark_ref}, which is the standard tool for analyzing network packets.

\subsection{Why We Use Wireshark}
NET\_SCAN works at the discovery layer. It finds open ports, looks up bugs, and guesses the attack paths. But to know for sure if a service is actually being exploited right now, you need to look at the raw network traffic. Wireshark lets us do deep packet inspection (DPI) which helps us in three main ways:
\begin{enumerate}
    \item \textbf{Traffic Validation:} Wireshark captures live network traffic on flagged interfaces, enabling defenders to verify whether vulnerable services (e.g., FTP on Port 21, SMB on Port 445) are actively transmitting unencrypted credentials or sensitive data.
    \item \textbf{Lateral Movement Confirmation:} By applying display filters targeting the specific port pairs identified in NET\_SCAN's attack chains (e.g., \texttt{tcp.port==21 \&\& tcp.port==22} for an FTP$\to$SSH pivot), analysts can confirm or refute whether inter-service communication patterns match the predicted lateral movement paths.
    \item \textbf{Protocol-Level Anomaly Detection:} Wireshark's protocol dissectors reveal malformed packets, unexpected protocol negotiations, and banner anomalies that static port scanning cannot detect \cite{sanders2017}.
\end{enumerate}

\subsection{Remediation Workflow}
The proposed remediation workflow operates in four phases, integrating NET\_SCAN's output with Wireshark-driven validation:

\subsubsection{Phase 1: Triage via NES Prioritization}
Defenders begin by reviewing NET\_SCAN's NES scores and attack chain enumeration. Networks scoring Critical (NES $\geq$ 81) are prioritized for immediate Wireshark capture sessions. The What-If Engine's per-port NES impact scores guide which services to inspect first.

\subsubsection{Phase 2: Live Traffic Capture \& Inspection}
Wireshark is deployed on the network segment under investigation. Capture filters are configured to isolate traffic on the specific ports flagged by NET\_SCAN. For example, for Network F (NES = 100), the capture filter \texttt{port 21 or port 53 or port 80 or port 443} isolates all traffic on the four highest-leverage ports. Analysts inspect:
\begin{itemize}
    \item \textbf{Unencrypted credential transmission} on FTP (Port 21) and HTTP (Port 80) using Wireshark's ``Follow TCP Stream'' feature.
    \item \textbf{DNS query patterns} on Port 53 to detect potential exfiltration channels (aligned with MITRE T1048).
    \item \textbf{SMB/NetBIOS handshakes} on Ports 139/445 to identify unauthorized file-sharing sessions or lateral movement attempts (aligned with MITRE T1210).
    \item \textbf{TLS certificate validity} on HTTPS (Port 443) and DNS-over-TLS (Port 853) to verify encryption integrity.
\end{itemize}

\subsubsection{Phase 3: Targeted Port Hardening}
Based on the combined evidence from NET\_SCAN's What-If analysis and Wireshark's packet-level findings, defenders execute targeted remediation actions:
\begin{itemize}
    \item \textbf{Service Decommissioning:} Disable unnecessary services confirmed as exploitable by Wireshark captures. For Network F, removing FTP (Port 21) eliminates the CVE-1999-0080 (CVSS 10.0) attack surface.
    \item \textbf{Protocol Upgrade:} Replace unencrypted protocols (FTP $\to$ SFTP, HTTP $\to$ HTTPS, DNS $\to$ DNS-over-TLS) where Wireshark confirms plaintext data transmission.
    \item \textbf{Firewall Rule Insertion:} Deploy stateful firewall rules blocking the specific inter-port communication patterns that NET\_SCAN's BFS/Dijkstra engine identified as lateral movement paths.
    \item \textbf{Network Segmentation:} Isolate high-risk service clusters (e.g., SMB/NetBIOS/RPC triangle in Network G) into dedicated VLANs with strict inter-VLAN ACLs.
\end{itemize}

\subsubsection{Phase 4: Post-Remediation Verification}
After remediation, the defender executes a second NET\_SCAN pass on the hardened network. The updated NES score is compared against the pre-remediation baseline to quantify improvement. Simultaneously, a Wireshark capture session verifies that the blocked ports no longer carry traffic and that protocol upgrades are functioning correctly. This closed-loop validation ensures that remediation actions have the intended effect and no residual attack surfaces remain.

\subsection{Illustrative Example: Network G Remediation}
Consider Network G (172.20.10.3, NES = 50, Medium), which exposed Ports 135 (RPC), 139 (NetBIOS), and 445 (SMB). The remediation workflow proceeds as follows:
\begin{enumerate}
    \item NET\_SCAN identifies 6 CVEs, 2 MITRE techniques (T1136, T1210), and a triangle attack topology.
    \item Wireshark capture on the local subnet confirms active SMB session negotiation on Port 445 and NetBIOS name resolution traffic on Port 139.
    \item The defender disables NetBIOS over TCP/IP in Windows network adapter settings and restricts SMB access via Windows Firewall to authorized hosts only.
    \item A re-scan with NET\_SCAN confirms NES reduction from 50 to $\leq$20 (Low), and Wireshark verifies zero traffic on Ports 139 and 445 from unauthorized sources.
\end{enumerate}

This framework transforms NET\_SCAN from a \emph{detection-only} tool into a component of a complete \emph{detect--validate--remediate--verify} security operations cycle, with Wireshark serving as the packet-level ground truth at each stage.

\section{Conclusion}
% ============================================================
This paper presented the architectural design and empirical validation of NET\_SCAN across \textbf{eight} heterogeneous network environments ranging from isolated campus interfaces to live internet-facing hosts. By bridging multi-threaded port sweeping with NVD-enriched CVE correlation, MITRE ATT\&CK technique mapping, dual-algorithm (BFS + Dijkstra) lateral movement pathfinding, What-If mitigation analysis, and real-time force-directed frontend visualization, the platform provides a scalable, browser-native solution to adversarial network topology analysis.

Testing confirmed that NET\_SCAN correctly produces zero false positives on hardened networks (Networks A, D), identifies and enriches legacy service vulnerabilities (Network B, NES: 20), reveals compound topological risk through multi-node attack path graphs (Networks C and G, NES: 50), distinguishes High-tier exposure on internet-facing hosts with modest lateral graphs (Network H, NES: 60), and scales to Critical-tier exposure on dense lateral movement graphs (Networks E and F, NES: 85 and 100 respectively). Across all eight environments, the lateral path multiplier $\alpha^{P}$ in the NES formula was empirically confirmed as the primary driver of tier escalation, validating the platform's mathematical foundation and its superiority over CVE-count-centric scoring approaches.
